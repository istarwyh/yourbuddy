# 典型工作流

[English](workflows.md) | 中文

这些是官网可展开为教程的任务路径。使用前完成[首次使用](quickstart.zh.md)；下列示例提示词是演示输入，不是已经执行的成功记录。各插件的能力与限制由[默认插件](plugins.zh.md)统一说明。

## 资料整理：从文件到可检查的摘要

准备一个只包含可公开文本或 Markdown 的练习目录，选择它作为工作区。示例请求：“阅读当前目录中的产品调研资料，整理一份 summary.md，区分原文事实、你的判断和仍需查证的问题，并给出来源文件。”

在对话中查看引用，通过 Better Sidebar 对照原文和输出。需要检索新资料时明确提出搜索请求，并检查来源；搜索结果与本地材料都不自动等于正确结论。

完成标准是摘要文件实际存在、关键判断有来源、未证实事项得到标注。官网配图展示原文、摘要与引用位置，不把未经验证的 PDF／Office 批处理能力加入本教程。

## 开发任务：从问题到差异与验证

准备一个可运行的小型练习仓库，说明问题、预期行为和可执行的验证方法。示例请求：“修复当前项目中的这个输入问题，先检查相关代码，修改后运行已有的针对性检查，并说明你实际验证了什么。”

通过 Better Sidebar 查看改动与命令结果。适合独立委派的任务可以交给 Codex Subagent，但应提供完整任务说明；它不会自动继承主会话全部上下文。需要用户输入或额外权限的任务可能不能由无人值守子任务完成。

完成标准是差异符合需求、检查结果可读取、失败和未验证项被说明。Git 提交、远端推送与部署是独立动作，教程应显式说明何时发生。

## 上下文诊断：先观察，再精简

选择一个已经积累项目指令或技能的会话。示例请求：“调用 context_audit，指出当前上下文中重复或被遮蔽的来源，先给出保留与精简建议，不修改文件。”

打开 Context Doctor 报告，确认路径、相同段落与技能胜出关系，再选择一个明确的问题进行修改。重新审计用于观察估算变化；再执行一个代表性任务，确认精简没有破坏必要行为。

完成标准是每项修改都有对应来源和用途判断，而非单纯追求更小的 Token 数。审计估算降低与模型质量提升分开报告。

## 评测冷启动：从已完成会话发现问题

在有近期已完成业务会话的同一工作目录中，调用 Harbor Skill 并说明“我还没有数据集，希望先看看最近任务有哪些可以改进的地方”。

先预览最多十个符合条件的历史会话。检查范围、评测器、预计请求与证据保存说明后，再确认执行。读取逐项证据、未评分原因与覆盖率，挑选值得保留的失败案例。

完成标准是得到可解释的历史诊断，而不是一个可晋级的 Candidate。历史记录不会重新生成答案，不能据此断言修改后的 Agent 已经变好；没有可用记录时，应完成业务任务或提供明确 Query／Dataset。

## 受控改进：固定基线，再改变一项因素

提供明确的任务集、Agent 入口、评分标准与优化者；确认后由 Skill 初始化评测，并检查所需环境。对 DSH Candidate 固定模型选择，先建立有效基线，再选择一个有证据的改进假设。

执行一次受控修改并在相同可比条件下回归，检查逐任务结果、总体覆盖率、回归和有效性；正式晋级还需要满足已接受的策略。如果改变了模型或评测器身份，应按工具提示建立新基线，避免比较不可比结果。

完成标准是结论有可比证据、已知回归和未验证项。业务部署仍由已有 CI/CD 或显式部署操作完成；Harbor 工作流不自行发布应用，也不自动保证评测器可靠。

## 演示取材规则

官网第一版优先录制“首次产物”和“历史会话诊断”两条短路径，分别说明日常工作与质量改进。使用当前 YourHarness 安装包、练习数据和真实可见入口；每份演示标注版本、前提与实际验证范围。完整的发行验收材料放在[发布记录](../../releases/README.zh.md)，不在宣传页面堆放内部日志。
