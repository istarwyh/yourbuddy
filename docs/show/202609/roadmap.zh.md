# 路线图：已有基础与建议方向

[English](roadmap.md) | 中文

## 建议方向一：完成首次使用与官网闭环

**优先级：近期优先。** 采用已调研的 OINK Starter 是建站建议；本次只交付内容方案。官网首先覆盖安装、模型配置、第一个任务、默认插件、常见问题和发布记录。让用户在一个短流程内从“这是什么”走到“我知道怎样检查自己的结果”。

**完成标准。** 在干净的受支持 Mac 上，从实际下载页安装对应版本，配置一种可用模型，选择工作区，生成并打开一个文件；失败时能够找到匹配的排障说明。中英文导航、搜索、下载链接和 Markdown 输出在部署地址验证通过。

**投入理由。** 新用户不能独立开始时，增加高级功能难以转化为价值。可复用的安装与演示证据也会减少文档与发行状态脱节。

## 建议方向二：让默认组合更容易理解和维护

**优先级：随后推进。** 完善插件来源、用途、默认／可选能力、环境前提与更新关系的呈现。针对登录失败、网络配置、插件安装后重启、上下文告警这些真实问题补齐操作说明与案例。

**完成标准。** 用户能解释自己正在使用哪条模型路由、哪些能力来自第三方；一次安装失败能定位到具体包；更新后默认插件仍能按当前版本文档使用。是否新增状态面板或统一设置，依据这些任务的实际阻碍决定。

**投入理由。** 默认预装减少了安装步骤，也带来了组合行为与维护责任。先让现有组合可靠且可解释，再扩充默认集合。

## 建议方向三：把评测变成可重复的改进习惯

**优先级：在真实案例上迭代。** 打通“历史诊断 → 人工确认失败案例 → 固定回归任务 → 一次修改 → 可比回归报告”的指导路径。现有评测与元评测能力继续使用，失败案例的整理体验和教程可以逐步补强。

**完成标准。** 至少一个经过脱敏的真实案例可以复现，并展示基线、变更、评测身份、覆盖率、回归与结论；资料清楚区分历史观察、快速诊断、正式评测和部署。评分依据不足时保留未评分或未验证状态。

**投入理由。** 自演进的可信度来自稳定任务上的可比较结果。先积累可复现案例，再决定是否增加自动化程度；不承诺无人值守持续自我修改或自动上线。

## 建议方向四：由用户需求决定扩展

**优先级：探索。** 收集跨平台、更多模型与插件、团队使用和更丰富个性化的具体任务需求。对每项需求先确认用户、频率、现有替代办法和维护成本，再建立独立方案。

**完成标准。** 每项拟纳入开发的能力至少有明确使用者、可运行场景、支持范围和验证方法；跨平台尤其需要真实安装、运行时、插件、更新和卸载路径的验证。

**投入理由。** 插件化允许按需要扩展，但不意味着每项扩展都适合默认内置。当前不把云同步、团队权限、移动端和全面跨平台作为已承诺功能。

## 公开路线页的表达

使用“正在实现”“候选方向”“探索中”等标签时，分别连接实际开发工作或方案；本页的建议在尚未启动前使用“候选方向”。避免只写“体验优化”“更强智能”等无法验收的条目。每个完成项都说明用户可以做什么，并链接[发行与验证记录](../../releases/README.zh.md)。
