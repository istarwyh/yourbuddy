<a id="scope"></a>
## 产品目标与范围

Y8 面向需要可靠默认体验、同时愿意为专业需求开发扩展的用户，首轮重点观察小团队中的插件维护者和直接使用插件的成员。用户不需要在第一次使用时理解 Cordis、Profile、Preset 或 Harbor 评测概念；开发者可以进入源码、配置和完整扩展接口。

DSH 的扩展机制提供定制深度，社区插件提供可复用能力，Y8 负责默认组合、开发引导、联调和交付体验。实验不以插件数量衡量成功，也不假定插件被收录就已兼容。团队共享首先验证插件和工作方法的复用；实时协同编辑、团队云端权限、公开市场建设和新增平台支持不在首轮范围内。

Harbor Self Evolving 是 Y8 维护者本人深度开发的独立项目，也是本方案的复杂项目样本。小型工具、界面插件和 Harbor 都参与验证，避免把 Python、容器和评测流程变成所有插件的前提。

<a id="design"></a>
## 拟验证的产品设计

本节描述实验原型需要提供的体验和约束。原型采用 DSH 现有接口，最终组件归属根据试验结果确定。

### 默认使用

首次使用只完成必要的模型接入、工作区选择和一个真实任务。首页呈现任务入口与成果；能力缺少账号或环境时显示具体补齐步骤。Harbor 等专业能力按任务需要引导，不把它们的全部依赖放进基础使用流程。

### 定义插件

扩展入口提供“寻找已有插件”“创建插件”“导入插件项目”。开发助手先检查现有能力，再建议配置、Skill、Preset、Bundle、MCP 或原生 Host／Client 插件；分类是实现选择，不要求用户先学习全部术语。

助手从需求、现有项目和运行时整理一份简短说明：用户入口、输入输出、依赖与配置、生效范围、验收样例。只有用户意图和不可推断的选择需要询问。修改现有插件时定位原项目和目标版本，避免生成一个功能相似但失去维护关系的新项目。

### 文档与开发助手

提供工具、界面、Host + Client 三类可运行模板，以及从创建、配置、调试到打包的指南。教程、模板和开发 Skill 使用同一组版本匹配的接口与样例；开发助手先读取当前运行时可用的服务、事件、工具和槽位，再生成代码。遇到接口不支持时明确说明，不回退到猜测内部方法。

模板保留普通本地源码、类型依赖、配置说明、构建入口和验收样例。用户可以通过外部编辑器或 AI 修改同一项目，Git 记录同一份改动。开发普通插件的目标前提是已安装 Y8 和插件开发依赖，无需构建整个 DSH 仓库或桌面壳；该体验仍需 E2 证明。

### 本地开发

Y8 原型从所选项目启动独立开发进程，使用单独的 Harness home、Profile 和测试目录；只复制用户明确选定的非敏感配置。插件注册的服务权限和文件访问仍需要独立约束，不能把换目录称为安全隔离。

开发视图同时呈现项目版本、DSH 版本、构建结果、Host 状态、Client 装载与渲染结果、依赖和错误来源。可重载的变化走现有开发机制；需要构建或重启时明确提示，并显示实际生效版本。停止插件需要验证注册和资源清理；已经写出的文件或外部副作用不会因停止自动撤销。

Y8 自有常规功能优先使用第三方也能使用的公开扩展接口。缺少接口时先定义拥有者和使用方，再决定新增扩展点；不引入仅供 Y8 插件使用的隐式特权接口，也不另建插件语言、打包格式或完整 IDE。

### 从试验到交付

临时试验采用已有动态工具；长期项目采用原生 DSH 包和 Bundle。原型只为明确支持的模板提供“保存为插件项目”，生成入口、依赖、构建配置并处理运行环境差异。动态 JavaScript 函数体不能直接视为 TypeScript／JSX 工程；不支持的转换需要说明原因并保留源码供继续开发。

分发携带构建产物、兼容版本、配置要求和验收样例，不携带私人会话、密钥、作者绝对路径或整个 Harness home。接收者自行绑定账号和目录。首轮用本地安装包验证交付，公开发布不作为实验前提。

<a id="method"></a>
## 实验组织与计量

建议招募来自三个小团队的六位专业用户，至少三位不熟悉 DSH 插件开发；每个团队包含维护者和使用者。Harbor 作者与一位非作者协作者另作复杂项目观察，不并入新手成功率。招募尚未开始；人数不足时只报告已观察人数，不外推总体结论。

每轮冻结安装包校验和、DSH／插件版本、操作系统与架构、模型配置、输入材料、验收标准和文档版本。首轮只覆盖选定安装包正式支持的一种平台，其他平台保持未验证。原型和对照使用相同模型与输入难度；外部服务故障单列原因，同时保留在端到端失败记录中。

比较三个条件：A 为冻结的现有产品与文档；B 只增加指南、模板和开发 Skill；C 在 B 上增加开发入口、独立实例与诊断工具。先冻结 A 并试跑基准材料，再准备 B 和 C；参与者的比较实验在对应条件齐备后执行。开发任务准备难度相近的变体，交叉安排顺序；仍有学习效应时单独报告，不把熟练带来的提速归因于原型。

总耗时从开始任务到达到验收条件计算；活跃耗时另外扣除已记录的下载、登录和远端等待。独立完成允许使用对应条件的文档和 AI，但不接受维护者现场指导；接受指导的任务可以完成，却不计为独立成功。帮助次数、错误接口引用、构建失败、重启次数、模型请求与费用可用性一并记录。计时上限内未完成计为失败；不可测费用记为未知。以下目标是首轮继续投入的门槛，不是对外性能承诺或统计显著性结论。

<a id="experiments"></a>
## 四组实验

每组先冻结任务和验收材料，再运行、记录并作出继续、修改或停止的决定。任何未执行项保留未运行状态。

### E0：默认体验

假设：用户无需开发插件或理解扩展架构，就能完成基础工作。任务为安装选定发行版、接入可用模型、选中练习目录，把给定资料整理为报告并打开检查；再次启动后找回成果和会话。资料含明确事实清单，验收检查事实覆盖、来源可定位和文件位置。

目标：六人中至少五人独立完成，完成者活跃耗时中位数不超过十五分钟；每人总计时上限四十五分钟。观察安装、账号、工作区和成果检查各步阻碍。缺少模型配置的负向案例必须指出缺什么及配置入口，不能呈现为已就绪。

若两人及以上无法独立完成，优先修复 E0 阻碍，再评估新增开发功能；开发能力的增加不能掩盖基础路径退化。

### E1：说明和引导

假设：经过验证的教程、模板和运行时感知的开发助手，能够降低首次开发成本。六位参与者完成相近的只读工具任务，例如读取结构化资料并返回汇总；分别使用 A 和 B，保持输入、模型和验收难度相当。

目标：B 条件至少五人独立完成工具注册、真实调用和结果检查，单次活跃耗时不超过四十五分钟，总计时上限九十分钟；配对活跃耗时中位数较 A 降低至少 25%。A 或 B 未完成的配对不计算耗时收益，但计入完成率；可比较配对少于四组时不宣布提速结论。

另设“现有 Skill 或配置已经足够”的需求，以及“指定接口不存在”的需求。助手分别说明更小的实现方式和缺失接口，不凭空补造方法。记录读文档、改代码和人工帮助的具体位置，判断问题来自说明还是工具。

### E2：本地开发与持续修改

假设：独立项目接入与集中诊断能缩短修改、观察和修复的往返。使用 B 与 C 比较小型工具、带配置的界面插件和 Host + Client 插件；Harbor 选择一次范围明确的真实小改动，由作者与非作者分别记录，避免和入门任务混算。

目标：三类模板均可在不构建整个 Y8／DSH 仓库的情况下完成创建或导入、构建、试跑、修改和停用。对支持重载的小型 Client 模板，预热后至少记录十次有效修改，保存到可见生效的中位数不超过十五秒；需要重启的修改另报，不混入重载数据。

负向案例包含缺失服务依赖、错误配置、Client 渲染错误和失败的版本更新。界面需区分失败阶段、目标版本和当前有效版本；修复或回到已验证版本后再次验收。通过真实调用和可见界面检查停用后的工具、监听与视图清理，不能仅检查状态标签。

Harbor 验证跨组件联调和安装依赖；涉及 Agent 效果的改动再用固定任务、模型和评测身份比较。Harbor 评测不替代类型检查、构建、界面或生命周期测试，具体使用限制由其产品文档维护。

### E3：保存、分享与维护

假设：试验或本地项目能够成为接收者可独立使用的插件。把支持的动态工具和界面试验保存为项目，并把一个已有项目打包；三份安装产物分别交给非作者在干净环境验收，至少覆盖两位接收者。

目标：三份产物均完成安装、配置、调用或界面检查、重启后使用、版本更新和恢复已验证版本；接收者不需要作者的仓库、目录布局或凭据。每份产物保留校验和，接收者使用的是被验证过的同一份构建结果。

负向案例包含不支持的试验转换、缺少构建入口、不兼容版本和缺少账号。前两者应阻止生成“可交付”结论，后两者应说明具体前提并保留已有可用版本。清理测试凭据，检查产物不含敏感信息；此检查不等于对插件代码的安全认证。

<a id="delivery"></a>
## 实施顺序与决策

原型按下表增量实现；各阶段只在前置证据成立后扩大范围。实现时再确定具体包和文件，不把拟议按钮或操作名称当成现有命令。

| 阶段 | 最小交付 | 进入下一阶段的条件 |
|---|---|---|
| 基线准备 | 冻结样本、材料、版本和记录模板，运行 A 条件与 E0 | 基础阻碍已归类，E0 达标，必要时包含修复后的复测 |
| 开发引导 | 三类可运行模板、任务式教程、版本匹配的开发 Skill | E1 支持继续投入；若说明已经足够，缩减 C 的范围 |
| 开发工具 | 项目导入、独立开发实例、诊断和明确的重载／重启反馈 | E2 在小项目与 Harbor 上分别形成结果 |
| 团队交付 | 有界的试验转项目、打包、接收者安装和升级检查 | E3 完成，更新不会破坏 E0 |

文档与模板维护者负责说明和示例，桌面维护者负责开发实例与安装体验，插件作者负责样本改动，非作者负责接收验收，实验记录者负责计时和结论。每轮开始前把这些角色落实到人员；不把提案本身当作排期或人力承诺。

代码实施按[测试政策](../../testing.zh.md)为实际改变的行为选择检查；用户或模型可见变化增加对应的真实可运行样例和快照。模板检查覆盖正常项目和一个能被顶层检查拒绝的无效项目；安装验证消费打包产物，避免工作区依赖掩盖遗漏。

若 E1 无收益，先检查需求分类、接口准确性和教程；若 E2 主要时间花在外部运行环境，先改环境诊断；若 E3 失败，暂停扩大模板与分发范围。出现数据泄露、日常实例被误改或无法恢复的更新时停止该原型，记录影响并修复后重新验收。
