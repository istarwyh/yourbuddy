# Agent Note: 版本化发布说明与验证资料归档

Status: implemented

[English](2026-09-06-release-notes-and-verification-archives.md) | 中文

## Problem

本仓库独立发布桌面应用、DSH、Vendored Cordis、Landlock、Python 与文档产品，各自采用不同版本线。现有流程定义了可复现构建与受保护发布，但没有持久记录把版本的用户可见变化与实际检查过的准确环境、操作旅程、失败状态和发布文件关联起来。因此，CI 成功、源码测试、临时工作流产物和当前分支文档可能被误认为完整产品发布。

发布说明还必须服务用户。提交列表或内部机制无法告诉用户改了什么、解决了什么问题、在哪里找到它，以及如何体验；从旧版本复制的截图也可能让未验证旅程看起来像本次实测。

## Decision

[`docs/releases/README.md`](../../../../docs/releases/README.zh.md)是面向用户的发布说明与验证资料归档的仓库单一参考。每个已发布 Tag 都有一个从仓库模板复制的 `docs/releases/<release-tag>/` 目录。仓库中各发布家族使用独立版本线，因此以完整 Tag 作为目录键。

版本页首先说明用户结果，然后记录场景级证据。每个场景都区分源码与正式包、本次证据与历史资料、合成数据与经过脱敏的真实数据，以及 Mock 或受控服务与具名真实供应商。报告保留失败、跳过与未验证状态；证据只能支持其记录环境与操作直接观察到的结论。

截图是可选资料。有价值的 UI 旅程保留相关的操作前、执行中、结果及失败恢复状态；非 UI 改动可以使用受限日志、校验和、注册表元数据或产物列表。只有脱敏副本可以进入 Git 或发布附件。

Tag 所指向的 Commit 包含归档与版本索引。公开发布页链接到该不可变证据 Commit，以及现有渠道提供的下载归档或 Tag 源码归档。发布后 Tag 与安装包保持不可变；需要修改已发布字节或面向用户的结论时使用新版本。

产品发布、验证资料完整性与未验证范围是三个独立状态。维护者必须核验当次发布涉及的真实 GitHub Release、更新渠道、npm 注册表、PyPI 注册表或文档 URL，不能从绿色工作流推断发布完成。

现有渠道文档与工作流继续管理版本源、发布命令、注册表和凭据。本约定不增加自定义脚本、CI 要求、审批或发布路径。

## Alternatives considered

**只使用传统 Changelog。** Changelog 可以概述用户可见变化，但不能保留场景环境、中间与失败状态、产物 Hash，以及源码验证与安装后产品验证之间的区别。

**只把证据保存在 CI 产物或发布评论中。** 临时产物会过期，评论可以脱离 Tag 源码被移动或编辑，而且两者都不能在发布前提供仓库内可审阅的双语记录。

**在 CI 中生成并强制执行发布证据 Schema。** 机械完整性不能证明截图来自本次验证，也不能证明真实产品旅程确实发生。新增门禁还会重复现有发布流程并增加维护成本，却无法验证最关键的真实性判断。

## Consequences

发布准备会在打 Tag 前增加一项轻量人工文档步骤，并在发布后增加一次真实目的地检查。模板使预期字段与当次交付清单易于发现，版本归档则可以和它描述的代码一起接受审阅。

本约定不会追溯验证此前发布的版本。只有某个发布包含完整或明确标记为部分完成的归档后，索引才会增加条目；后续证据只有在标明实际日期、受测构建与限制时，才能描述旧版本。

现有 Markdown 与翻译检查可以发现仓库链接损坏和双语文件不一致，但没有自动化检查能够证明发布证据真实或完整。审阅者与发布操作人员继续承担这项责任。
