# Agent Note: YourBuddy application-wide network proxy

Status: implemented

English | [中文](2026-08-30-yourbuddy-global-network-proxy.zh.md)

## Problem

Applications launched from macOS Finder do not inherit proxy variables from a user's interactive shell. A plugin such as Codex Auth can therefore create a Node HTTP client that connects directly even when macOS has a working system proxy. Solving only one plugin leaves package installation, marketplace metadata, runtime provisioning, and application updates on different routes.

## Decision

YourBuddy's native desktop settings own one application-wide `direct`, `system`, or `custom` proxy selection. Direct is the default and removes inherited upper- and lower-case proxy variables from every application-owned process. System mode runs the fixed `/usr/sbin/scutil --proxy` command and accepts fixed macOS HTTP and HTTPS endpoints. Custom mode requires separate credential-free HTTP and HTTPS URLs and accepts a comma-separated bypass list. Every mode adds `localhost`, `127.0.0.1`, and `::1` to the bypass list so the Tauri WebView and private Host remain on loopback.

The native boot path resolves the persisted selection before runtime provisioning. The resolved policy configures Rust HTTP clients, the signed updater, native Host and plugin subprocesses, Profile repair and package installation, toolchain downloads, and WSL commands. Every native reqwest client built through this policy uses rustls with the platform certificate verifier, so macOS Keychain trust applies to HTTPS intercepted by an enterprise proxy. Additional trust has one precedence order: an explicitly selected CA path, otherwise `NODE_EXTRA_CA_CERTS` from the launch process or macOS `launchctl`, otherwise system trust alone. The native owner canonicalizes each candidate `.pem` or `.crt` path, verifies that the bounded regular file contains valid X.509 certificates whose validity interval includes the current time, and persists only an explicitly selected path. Environment injection removes ambient proxy and CA values before applying that resolved path and its source, sets Node's environment-proxy switch explicitly, adds `--use-system-ca` through `NODE_OPTIONS`, and sets the validated `NODE_EXTRA_CA_CERTS` path before every application-owned Node process starts; WSL commands receive the equivalent mounted path. Because Node reads the extra-CA variable only at process startup, saving the setting terminates and waits for the current private Host before YourBuddy relaunches it. Because the bundled Node 22.19 runtime predates the environment-proxy switch, the DSH CLI also materializes its layered environment, installs Undici's `EnvHttpProxyAgent` as the process-global dispatcher, and only then imports Profile boot and configured plugins. Dispatcher ownership stays at the CLI process entry rather than a product plugin, so provider initialization order cannot leave Host global `fetch` on the default direct dispatcher. The running application keeps this immutable resolved value; changing the persisted draft cannot split a live Host process tree.

System mode rejects PAC, automatic discovery, and HTTP-only macOS configurations. PAC evaluation is not equivalent to exporting static Node proxy variables, and an HTTP-only macOS setting would let HTTPS clients silently choose another route. Custom proxy URLs reject embedded credentials and non-HTTP schemes so secrets do not enter the plaintext desktop settings file, process arguments, or logs. The two custom fields describe the proxy used for HTTP-target and HTTPS-target requests rather than the proxy server's own transport; if an `http://` and `https://` pair names the same loopback host and port, the HTTPS-target value is canonicalized to `http://` so a local HTTP CONNECT proxy is not mistaken for a TLS proxy. Remote endpoints retain the explicit scheme and fail their preflight if misconfigured. The optional CA input rejects relative, missing, unreadable, non-regular, oversized, DER-only, malformed, not-yet-valid, and expired certificate files. It supplements platform trust rather than trusting every Keychain entry indiscriminately or replacing system roots. Authenticated proxies require a future credential-store integration instead of a compatibility fallback.

The Personal Workbench Client contributes a General settings card that loads the current native setting and detected macOS endpoints, opens a restricted native CA file picker, and tests the native draft, a fresh managed Node process using the installed runtime and Undici `EnvHttpProxyAgent`, and the running Node Host separately against `https://chatgpt.com/`. Saving repeats the native and managed Node preflights and persists nothing unless both pass. The running Node Host test requires process-local proof that the CLI installed its Dispatcher before it uses a fixed same-origin JSON POST and global `fetch`. The probes return only success, HTTP status, whether the proxy route is active, the resolved proxy mode, the CA source (`system`, `environment`, or `custom`), and a bounded transport or certificate code; the card labels each result separately, including codes such as `UNKNOWN_ISSUER` and `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, instead of replacing a failure with a generic proxy-process diagnosis. No test requires or transmits a ChatGPT credential, and none returns a proxy URL, CA path, or raw request error to the browser. Certificate failures direct the user to trust the enterprise root in macOS Keychain or choose its PEM bundle and state that YourBuddy keeps certificate verification enabled. A draft whose proxy mode or CA source differs from the active Host reports that a save, restart, and second test are required. Standalone `dsh web` renders the controls disabled because it has no trusted native owner.

The loopback Client uses a dedicated versioned message channel with `get`, `select-ca`, `test`, and `save` actions. The Tauri shell requires the exact workbench iframe source and Host origin, validates bounded fields and known keys, maps actions to four literal commands, and sends responses only to that origin. The `select-ca` action exposes a dedicated Rust command backed by Tauri's native dialog rather than generic filesystem access, and Rust validates the chosen file before returning its path. Rust performs the same settings validation again before test, save, or boot. The browser cannot provide a command name, executable, destination URL, system command, arbitrary file path, or arbitrary environment value.

The existing [YourBuddy product workbench distribution](2026-08-22-yourbuddy-product-workbench.md) remains the owner of product packaging and release acceptance. This note owns only the application-wide routing policy. The older [desktop host environment and home adoption](2026-08-14-desktop-host-env-and-home-adoption.md) remains applicable to Host executable discovery and environment isolation; proxy variables are now an explicit product-owned subset rather than inherited shell state.

## Alternatives considered

**Add a Codex-only proxy field.** Rejected because the same Node process tree also owns plugin discovery, installation, Harbor helpers, and other providers. Per-plugin proxy settings would create conflicting routes and duplicate secret-handling decisions.

**Inherit all Finder or shell network variables.** Rejected because Finder does not reliably receive interactive-shell proxy variables, ambient proxy values cannot express an explicit Direct choice, and inherited credentials could leak into child processes. The single credential-free `NODE_EXTRA_CA_CERTS` path is instead accepted as a launch-time trust input only after native validation and is replaced by an explicit desktop selection.

**Translate PAC or auto-discovery output to one static URL.** Rejected because those mechanisms select routes per request and may execute platform policy. Claiming support through one exported URL would be incorrect.

**Persist authenticated proxy URLs.** Rejected because the desktop settings file, process environment, diagnostics, and child processes are not a credential store.

**Disable TLS certificate verification.** Rejected because it would make every application-owned HTTPS request vulnerable to interception. Enterprise interception must be authorized by a platform-trusted root or one explicitly selected bundle; YourBuddy never sets `NODE_TLS_REJECT_UNAUTHORIZED=0`.

**Export every macOS Keychain certificate into Node.** Rejected because Keychain contains certificates with different trust settings and purposes. `--use-system-ca` adopts the operating system's trust decisions, while the explicit bundle gives the user a narrow addition when the embedded Node runtime cannot validate the corporate chain.

## Consequences

One visible setting routes Codex Auth, other Host plugins, package installation, runtime downloads, and signed updates consistently after restart. The current machine's fixed macOS proxy, Keychain-trusted enterprise roots, and valid launch-time `NODE_EXTRA_CA_CERTS` can be adopted without reselecting a CA, while Direct remains an explicit deterministic proxy state and an explicit CA selection remains authoritative. A user of PAC, automatic discovery, an HTTP-only proxy, proxy authentication, or an invalid interception certificate receives a specific failure and must correct the applicable proxy or trust setting. A selected or inherited CA path becomes an application startup dependency: moving or deleting the file causes the resolved policy to fail loudly instead of silently returning to a different trust policy. Custom endpoints used with WSL must be reachable from the WSL network namespace, and the additional CA file must be visible through its translated WSL mount path. The release gate starts the actual CLI Node Host with the archived Node 22.19 runtime, requires its global fetch to traverse a local HTTP CONNECT proxy, proves that the private CA fails without pre-start injection, and proves that the same Host succeeds when the validated CA path is present. The product release smoke exercises the trusted picker bridge, three distinct native-draft, managed-Node-draft, and running-Host outcomes, certificate guidance, guarded save, and restart journey. Rust tests cover system parsing, CA precedence and current validity, local proxy canonicalization and bypass, replacement and reinjection of ambient CA values, platform-verifier construction with extra roots, pre-start Node injection, WSL path translation, and bounded certificate codes.
