# Agent Note: YourHarness application-wide network proxy

Status: implemented

English | [中文](2026-08-30-yourharness-global-network-proxy.zh.md)

## Problem

Applications launched from macOS Finder do not inherit proxy variables from a user's interactive shell. A plugin such as Codex Auth can therefore create a Node HTTP client that connects directly even when macOS has a working system proxy. Solving only one plugin leaves package installation, marketplace metadata, runtime provisioning, and application updates on different routes.

## Decision

YourHarness's native desktop settings own one application-wide `direct`, `system`, or `custom` proxy selection. Direct is the default and removes inherited upper- and lower-case proxy variables from every application-owned process. System mode runs the fixed `/usr/sbin/scutil --proxy` command and accepts fixed macOS HTTP and HTTPS endpoints. Custom mode requires separate credential-free HTTP and HTTPS URLs and accepts a comma-separated bypass list. Every mode adds `localhost`, `127.0.0.1`, and `::1` to the bypass list so the Tauri WebView and private Host remain on loopback.

The native boot path resolves the persisted selection before runtime provisioning. The resolved policy configures Rust HTTP clients, the signed updater, native Host and plugin subprocesses, Profile repair and package installation, toolchain downloads, and WSL commands. Every native reqwest client built through this policy uses rustls with the platform certificate verifier, so macOS Keychain trust applies to HTTPS intercepted by an enterprise proxy. A user may additionally select one absolute PEM-encoded `.pem` or `.crt` CA bundle. The native owner canonicalizes the path, verifies that the bounded regular file contains certificates, persists only the canonical path, and adds those roots to the platform verifier used by reqwest and the updater. Environment injection removes ambient proxy values and `NODE_EXTRA_CA_CERTS` before applying the resolved values, sets Node's environment-proxy switch explicitly, adds `--use-system-ca` through `NODE_OPTIONS`, and sets the selected `NODE_EXTRA_CA_CERTS` path before every application-owned Node process starts; WSL commands receive the equivalent mounted path. Because Node reads the extra-CA variable only at process startup, saving the setting terminates and waits for the current private Host before YourHarness relaunches it. Because the bundled Node 22.19 runtime predates the environment-proxy switch, the DSH CLI also materializes its layered environment, installs Undici's `EnvHttpProxyAgent` as the process-global dispatcher, and only then imports Profile boot and configured plugins. Dispatcher ownership stays at the CLI process entry rather than a product plugin, so provider initialization order cannot leave Host global `fetch` on the default direct dispatcher. The running application keeps this immutable resolved value; changing the persisted draft cannot split a live Host process tree.

System mode rejects PAC, automatic discovery, and HTTP-only macOS configurations. PAC evaluation is not equivalent to exporting static Node proxy variables, and an HTTP-only macOS setting would let HTTPS clients silently choose another route. Custom proxy URLs reject embedded credentials and non-HTTP schemes so secrets do not enter the plaintext desktop settings file, process arguments, or logs. The optional CA input rejects relative, missing, non-regular, oversized, DER-only, and non-certificate files. It supplements platform trust rather than trusting every Keychain entry indiscriminately or replacing system roots. Authenticated proxies require a future credential-store integration instead of a compatibility fallback.

The Personal Workbench Client contributes a General settings card that loads the current native setting and detected macOS endpoints, opens a restricted native CA file picker, and tests the desktop draft and the running Node Host separately against `https://chatgpt.com/`. The Node Host test requires process-local proof that the CLI installed its Dispatcher before it uses a fixed same-origin JSON POST and global `fetch`. Both probes return only success, HTTP status, whether the proxy route is active, the resolved proxy mode, the CA source (`system` or `custom`), and a bounded transport or certificate code; the card labels each result separately, including codes such as `UNKNOWN_ISSUER` and `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, instead of replacing either failure with a generic proxy-process diagnosis. Neither test requires or transmits a ChatGPT credential, and neither returns a proxy URL, CA path, or raw request error to the browser. Certificate failures direct the user to trust the enterprise root in macOS Keychain or choose its PEM bundle and state that YourHarness keeps certificate verification enabled. A draft whose proxy mode or CA source differs from the active Host reports that a save, restart, and second test are required. Standalone `dsh web` renders the controls disabled because it has no trusted native owner.

The loopback Client uses a dedicated versioned message channel with `get`, `select-ca`, `test`, and `save` actions. The Tauri shell requires the exact workbench iframe source and Host origin, validates bounded fields and known keys, maps actions to four literal commands, and sends responses only to that origin. The `select-ca` action exposes a dedicated Rust command backed by Tauri's native dialog rather than generic filesystem access, and Rust validates the chosen file before returning its path. Rust performs the same settings validation again before test, save, or boot. The browser cannot provide a command name, executable, destination URL, system command, arbitrary file path, or arbitrary environment value.

The existing [YourHarness product workbench distribution](2026-08-22-yourharness-product-workbench.md) remains the owner of product packaging and release acceptance. This note owns only the application-wide routing policy. The older [desktop host environment and home adoption](2026-08-14-desktop-host-env-and-home-adoption.md) remains applicable to Host executable discovery and environment isolation; proxy variables are now an explicit product-owned subset rather than inherited shell state.

## Alternatives considered

**Add a Codex-only proxy field.** Rejected because the same Node process tree also owns plugin discovery, installation, Harbor helpers, and other providers. Per-plugin proxy settings would create conflicting routes and duplicate secret-handling decisions.

**Inherit the Finder or shell environment.** Rejected because Finder does not reliably receive interactive-shell variables, ambient values cannot express an explicit Direct choice, and inherited credentials could leak into child processes.

**Translate PAC or auto-discovery output to one static URL.** Rejected because those mechanisms select routes per request and may execute platform policy. Claiming support through one exported URL would be incorrect.

**Persist authenticated proxy URLs.** Rejected because the desktop settings file, process environment, diagnostics, and child processes are not a credential store.

**Disable TLS certificate verification.** Rejected because it would make every application-owned HTTPS request vulnerable to interception. Enterprise interception must be authorized by a platform-trusted root or one explicitly selected bundle; YourHarness never sets `NODE_TLS_REJECT_UNAUTHORIZED=0`.

**Export every macOS Keychain certificate into Node.** Rejected because Keychain contains certificates with different trust settings and purposes. `--use-system-ca` adopts the operating system's trust decisions, while the explicit bundle gives the user a narrow addition when the embedded Node runtime cannot validate the corporate chain.

## Consequences

One visible setting routes Codex Auth, other Host plugins, package installation, runtime downloads, and signed updates consistently after restart. The current machine's fixed macOS proxy and Keychain-trusted enterprise roots can be adopted without launching YourHarness from a terminal, while Direct remains an explicit deterministic state. A corporate root missing from the embedded Node trust path can be selected explicitly without weakening TLS verification. A user of PAC, automatic discovery, an HTTP-only proxy, proxy authentication, or an invalid interception certificate receives a specific failure and must correct the applicable proxy or trust setting. The persisted CA path becomes an application startup dependency: moving or deleting the file causes the resolved policy to fail loudly instead of silently returning to a different trust policy. Custom endpoints used with WSL must be reachable from the WSL network namespace, and the selected CA file must be visible through its translated WSL mount path. A real CLI Profile regression requires global HTTP fetch to traverse a local proxy, observes HTTPS `CONNECT`, and proves `NO_PROXY` bypass; the release smoke exercises the trusted picker bridge, separate desktop and Host mode and CA outcomes, certificate guidance, save, and restart journey. A real Node subprocess TLS test proves the private CA fails without pre-start injection and succeeds with `NODE_EXTRA_CA_CERTS`. Rust tests cover system parsing, CA file validation, local bypass, removal of ambient proxy and CA variables, platform-verifier construction with extra roots, pre-start Node injection, WSL path translation, and bounded certificate codes.
